# Project-5: Retail Sales Data Warehouse Design Using Star Schema

## 📌 Project Overview

This project implements a **Retail Sales Data Warehouse using Star Schema architecture in Snowflake**.

The objective is to organize retail sales data into a central fact table surrounded by dimension tables so that the warehouse can efficiently support **OLAP, Business Intelligence (BI), analytical reporting, and dashboards**.

The project is based on retail transactions generated from multiple branches across India and supports analysis of customers, products, branches, dates, revenue, sales trends, and regional performance.

---

## 🎯 Objectives

* Design a Star Schema for retail sales analytics.
* Identify the fact table and dimension tables.
* Define primary keys and foreign keys.
* Define measures and their types.
* Load source CSV files into Snowflake.
* Create staging, dimension, and fact tables.
* Establish relationships between fact and dimension tables.
* Perform analytical queries using the Star Schema.
* Support BI dashboards and OLAP reporting.

# ⭐ Star Schema Design

The warehouse follows a **Star Schema** with `FACT_SALES` as the central fact table.

```text
                         DIM_CUSTOMER
                              |
                              |
                              |
DIM_PRODUCT ----------- FACT_SALES ----------- DIM_DATE
                              |
                              |
                         DIM_BRANCH
```

---

## 📌 Fact Table

### FACT_SALES

`FACT_SALES` stores all retail sales transactions.

| Column         | Type        | Description               |
| -------------- | ----------- | ------------------------- |
| `SALE_ID`      | Primary Key | Unique sales transaction  |
| `CUSTOMER_ID`  | Foreign Key | References `DIM_CUSTOMER` |
| `PRODUCT_ID`   | Foreign Key | References `DIM_PRODUCT`  |
| `BRANCH_ID`    | Foreign Key | References `DIM_BRANCH`   |
| `DATE_ID`      | Foreign Key | References `DIM_DATE`     |
| `QUANTITY`     | Measure     | Number of products sold   |
| `TOTAL_AMOUNT` | Measure     | Total transaction amount  |

### Grain

One record in `FACT_SALES` represents the sale of **one product purchased by one customer from one retail branch on one specific date**.

### Measures

| Measure        | Type     |
| -------------- | -------- |
| `QUANTITY`     | Additive |
| `TOTAL_AMOUNT` | Additive |

# 🔗 Relationships

The Star Schema contains one-to-many relationships between each dimension and the fact table.

```text
DIM_CUSTOMER (1) --------< FACT_SALES (M)

DIM_PRODUCT  (1) --------< FACT_SALES (M)

DIM_BRANCH   (1) --------< FACT_SALES (M)

DIM_DATE     (1) --------< FACT_SALES (M)
```

A single customer can have multiple sales transactions.

A single product can appear in multiple sales transactions.

A single branch can generate multiple sales transactions.

A single date can contain multiple sales transactions.

# 🔍 Example Analytical Queries

## Customer-wise Sales

```sql
SELECT
    C.CUSTOMER_ID,
    C.CUSTOMER_NAME,
    SUM(F.QUANTITY) AS TOTAL_QUANTITY,
    SUM(F.TOTAL_AMOUNT) AS TOTAL_REVENUE
FROM FACT_SALES F
JOIN DIM_CUSTOMER C
    ON F.CUSTOMER_ID = C.CUSTOMER_ID
GROUP BY
    C.CUSTOMER_ID,
    C.CUSTOMER_NAME
ORDER BY TOTAL_REVENUE DESC;
```

## Product-wise Revenue

```sql
SELECT
    P.PRODUCT_ID,
    P.PRODUCT_NAME,
    SUM(F.QUANTITY) AS TOTAL_QUANTITY,
    SUM(F.TOTAL_AMOUNT) AS TOTAL_REVENUE
FROM FACT_SALES F
JOIN DIM_PRODUCT P
    ON F.PRODUCT_ID = P.PRODUCT_ID
GROUP BY
    P.PRODUCT_ID,
    P.PRODUCT_NAME
ORDER BY TOTAL_REVENUE DESC;
```

## Monthly Revenue

```sql
SELECT
    D.YEAR,
    D.MONTH,
    SUM(F.TOTAL_AMOUNT) AS MONTHLY_REVENUE
FROM FACT_SALES F
JOIN DIM_DATE D
    ON F.DATE_ID = D.DATE_ID
GROUP BY
    D.YEAR,
    D.MONTH
ORDER BY
    D.YEAR,
    D.MONTH;
```

## Category-wise Revenue

```sql
SELECT
    P.CATEGORY,
    SUM(F.TOTAL_AMOUNT) AS TOTAL_REVENUE
FROM FACT_SALES F
JOIN DIM_PRODUCT P
    ON F.PRODUCT_ID = P.PRODUCT_ID
GROUP BY P.CATEGORY
ORDER BY TOTAL_REVENUE DESC;
```

# 🚀 Advantages of Star Schema

* Simple and easy to understand.
* Requires fewer joins for analytical queries.
* Optimized for OLAP operations.
* Suitable for Business Intelligence dashboards.
* Improves report generation performance.
* Simplifies data analysis for business users.
* Provides an intuitive structure for analytical reporting.

---

# 🔄 OLTP vs Star Schema

| Operational Database   | Star Schema           |
| ---------------------- | --------------------- |
| Normalized             | Denormalized          |
| OLTP                   | OLAP                  |
| Frequent Updates       | Read Optimized        |
| Transaction Processing | Analytical Reporting  |
| Complex Joins          | Simple Joins          |
| Day-to-Day Operations  | Business Intelligence |
