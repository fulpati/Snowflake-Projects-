# 🛒 Project 14A: E-Commerce Web Event Analytics

## 📌 Overview

This project demonstrates an **E-Commerce Web Event Analytics pipeline in Snowflake**, comparing **Data Lake (Schema-on-Read)** and **Data Warehouse (Schema-on-Write)** approaches.

The system processes raw JSON clickstream events generated by an e-commerce platform, including:

- Page views
- Cart updates
- Purchases
- Order information
- Promotional codes
- Discount amounts

The project also demonstrates how the architecture handles **schema evolution, corrupted records, financial analytics, funnel metrics, and warehouse backfilling**.

---

## 🎯 Objective

The main objective is to demonstrate the difference between:

### Data Lake — Schema-on-Read

Raw JSON payloads are stored directly in a Snowflake `VARIANT` column without requiring a predefined relational schema.

This allows new fields to be introduced without immediately modifying the table structure.

### Data Warehouse — Schema-on-Write

The raw JSON data is extracted, transformed, and loaded into a structured relational table with predefined columns and data types.

This provides structured data suitable for analytics and reporting.

## 📂 Input Data

The input consists of three JSON batches.

### Batch 1 — Standard Structure

Contains 5 standard e-commerce events.

Examples include:

- Product views
- Cart additions
- Purchases

### Batch 2 — Schema Evolution

Contains 5 events and introduces two new fields:

```text
promo_code
discount_amount
```

These fields were not present in Batch 1.

Because the lake layer stores the payload as `VARIANT`, no table schema modification was required.

### Batch 3 — Edge Cases & Corrupted Record

Contains:

- 1 valid zero-value purchase
- 1 malformed JSON payload

The malformed payload is:


## 🗄️ Snowflake Objects

### 1. Raw Data Lake Table

```sql
CREATE OR REPLACE TABLE LAKE_RAW_EVENTS (
    RAW_EVENT VARIANT
);
```

The complete JSON payload is stored in a single `VARIANT` column.

This represents the **schema-on-read** layer.

---

### 2. Internal Stage

```text
@ECOMMERCE_RAW_STAGE
```

The input JSON files are staged before ingestion.

Files:

```text
batch1.json
batch2.json
batch3.json
```

---

### 3. Structured Data Warehouse Table

```sql
DW_STRUCTURED_EVENTS
```

Contains typed relational columns:

```text
EVENT_ID
EVENT_TIME
USER_ID
PAGE
ACTION
ORDER_TOTAL
SHIPPING_COST
TAX
ITEMS
PROMO_CODE
DISCOUNT_AMOUNT
NET_REVENUE
```

This represents the **schema-on-write** layer.

---

### 4. Quarantine Table

```sql
QUARANTINE_RAW_EVENTS
```

Used to isolate malformed records instead of allowing corrupted data into the analytical tables.

Columns:

```text

REASON
```

# 🔄 Data Ingestion Process

## Step 1 — Stage JSON Files

The JSON files are uploaded to:

```text
@ECOMMERCE_RAW_STAGE
```

---

## Step 2 — Load Raw JSON

The valid JSON records are loaded into:

```text
LAKE_RAW_EVENTS
```

using Snowflake's `COPY INTO` command.

Batch 3 uses:

```sql
ON_ERROR = 'CONTINUE'
```

so that the valid record can be loaded while the malformed JSON record is skipped.

# 🔍 Schema-on-Read

JSON attributes are extracted directly from the `VARIANT` column.

Example:

```sql
SELECT
    RAW_EVENT:event_id::STRING AS EVENT_ID,
    RAW_EVENT:timestamp::TIMESTAMP AS EVENT_TIME,
    RAW_EVENT:user_id::NUMBER AS USER_ID,
    RAW_EVENT:action::STRING AS ACTION,
    RAW_EVENT:order:total::NUMBER(12,2) AS ORDER_TOTAL,
    RAW_EVENT:promo_code::STRING AS PROMO_CODE
FROM LAKE_RAW_EVENTS;
```

The nested JSON structure can therefore be queried without first converting the raw data into a relational schema.

For example:

```text
RAW_EVENT:order:total
RAW_EVENT:order:shipping_cost
RAW_EVENT:order:tax
RAW_EVENT:promo_code
RAW_EVENT:discount_amount
```

# 💰 Financial Analysis

The project calculates:

```text
NET_REVENUE =
ORDER_TOTAL
- SHIPPING_COST
- TAX
- DISCOUNT_AMOUNT
```

When `discount_amount` is unavailable, it is treated as zero using `COALESCE()`.

```sql
COALESCE(
    RAW_EVENT:discount_amount::NUMBER(12,2),
```

```text
ORDER_TOTAL > 0
```

# 🚨 Error Handling & Quarantine

The malformed record:

```text
INVALID_JSON_PAYLOAD_MALFORMED_STRING
```

is not loaded into the raw JSON table.

It is instead recorded in:

```text
QUARANTINE_RAW_EVENTS
```

with the reason:

```text
MALFORMED_JSON_BODY
```

### Expected Quarantine Record

| Quarantine ID | Raw Record | Reason |
|---:|---|---|
| 1 | `INVALID_JSON_PAYLOAD_MALFORMED_STRING` | `MALFORMED_JSON_BODY` |

This prevents corrupted records from entering downstream analytical tables.

# 🔄 Schema Evolution Demonstration

One of the key concepts demonstrated by this project is schema evolution.

### Batch 1

```json
{
  "event_id": "EVT-8001",
  "action": "purchase",
  "order": {
    "total": 12500.00
  }
}
```

### Batch 2

New fields are introduced:

```json
{
  "event_id": "EVT-8006",
  "action": "purchase",
  "promo_code": "SUMMER20",
  "discount_amount": 3600.00
}
```

The `LAKE_RAW_EVENTS` table does **not** need to be altered because the entire payload is stored as:

```text
VARIANT
```

The new fields can simply be extracted when required.

This demonstrates the flexibility of **schema-on-read** storage.

In contrast, the structured warehouse requires predefined columns such as:

```text
PROMO_CODE
DISCOUNT_AMOUNT
```

before those fields can be stored relationally.
